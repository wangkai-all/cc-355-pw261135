# 离线现场采样 · 任务重分配与冲突裁决演示系统

现场采样端在**离线**状态下仍可填写记录；恢复上传时，服务器可能已经把未完成任务转给了另一台设备。
本系统演示如何保证：**真实采样不丢失、新承接者的成果不被覆盖、任务归属与事实记录分别保存、冲突进入可审阅队列、裁决后统计自动更新，且每个决定都可追溯。**

> ⚠️ 所有设备、人员、区域、采样数据均为**虚构样本**，系统不采集任何个人真实信息（记录中带 `synthetic: true` 标记）。

## 架构

```
浏览器（两台采样设备）                    管理台（管理员）
 client.html?c=dev-a / dev-b              admin.html
   离线: localStorage 发件箱
        │                                       │
        ▼                                       ▼
 ┌────────────── Web 网关 :4100（静态资源 + 反向代理，/internal 不对外）──────────────┐
 ▼                                                                                  ▼
 任务服务 :4101 (data/task.db)                     接收入库服务 :4102 (data/ingest.db)
 · 设备/令牌/连接切断（网页可切断某端）             · 两级幂等：batch_id 批次级 + (client,record_id) 记录级
 · 整任务锁定 / 采样点细粒度领取两种策略            · 事实记录与任务归属分离：谁采的样永久保留
 · 归属历史（只追加，不覆盖）+ 审计                 · 冲突队列：open 唯一(部分索引)，裁决中数据追加为候选
 · 内部接口供入库服务做归属判定/自动领取            · 四种裁决 + 裁决快照 + 审计 + 实时统计
```

零第三方运行时依赖，仅使用 Node.js 内置模块（要求 Node ≥ 22.5，开发环境为 Node 24，内置 `node:sqlite`）。

## 启动

```bash
npm run seed     # 写入虚构种子数据（同时清空两个库）
npm run dev      # 同时启动三个服务（Ctrl+C 一起退出）
```

- 采样端甲：http://127.0.0.1:4100/client.html?c=dev-a
- 采样端乙：http://127.0.0.1:4100/client.html?c=dev-b
- 管理台：　http://127.0.0.1:4100/admin.html

也可以分三个终端运行 `npm run start:task` / `start:ingest` / `start:web`。

## 核心设计如何对应需求

| 需求 | 实现 |
| --- | --- |
| 离线仍能填写 | 采样端所有记录先进 localStorage 发件箱，稳定 `record_id` 离线生成；"离线模式"开关在本机拦截全部请求 |
| 旧端数据不能丢、不能覆盖新成果 | 上传先无条件落 `sample_records` 事实表；无写入资格时状态置 `conflict` 进队列，现任 `canonical` 基准不动 |
| 任务归属与事实记录分别保存 | 归属只存在任务服务（`task_ownership` / `point_claims` 历史表，只追加不覆盖）；入库服务通过内部接口实时判定，不复制归属 |
| 冲突可审阅 | 管理台冲突队列：候选对比、角色（incumbent/late/followup/manual）、裁决理由强制填写、前后状态快照 |
| 整任务锁定 vs 细粒度领取 | `tasks.lock_mode = whole | points`；whole 按任务归属判定，points 按点领取判定，无人持有时首次上传自动领取；whole 任务也支持点级改派 |
| 上传成功回执丢失 | 批次表冻结首份回执；同 `batch_id` 重传返回 `replay:true` 的原回执，不重复处理；客户端另有显式回执查询接口 |
| 重复提交 | 同设备同 `record_id` 主键去重，返回 `duplicate` 并指向首次入库记录 |
| 裁决中再次来数据 | 同键 open 冲突唯一（SQLite 部分唯一索引）；新数据追加为 `followup` 候选，冲突不被覆盖 |
| 裁决后又来数据 | 新建冲突并以 `followup_of` 指向原冲突，原因标记 `post_resolution_new_data` |
| 裁决后统计更新 | 统计由事实表实时聚合（canonical 点数、accepted 数、冲突数、rejected/quarantined 数），无需手工维护 |
| 网页切断/重分配/补传/追溯 | 管理台五个页签全部覆盖；任务服务与入库服务各有独立审计流，记录操作者、理由与 JSON 详情 |

### 四种裁决动作

1. **采纳候选** `accept_record`：所选记录成为该点 canonical，同点其他候选降级为 rejected（事实保留）。
2. **全部不采纳** `reject_all`：现任 canonical 继续为准；无基准时该点留空，所有候选保留可查。
3. **合并保留** `merge_keep_canonical`：现任基准不变，迟到记录采纳为补充事实（accepted=1, canonical=0）。
4. **人工录入** `manual_entry`：管理员录入复核版本成为新基准，候选全部降级保留。

## 推荐演示剧本

1. 打开设备甲，在线保存并同步 1~2 条记录 → 状态"已采纳"。
2. 设备甲勾选"离线模式"，再保存 2 条记录（只进发件箱）。
3. 管理台**切断设备甲**，把 `task-lake` 整任务**重分配给设备乙**（填写理由）。
4. 设备乙在同一采样点 S01 上传新成果 → 乙成为基准，甲的旧记录自动降级但保留。
5. 设备甲取消离线 → 自动同步：数据进入**冲突队列**而非被丢弃或覆盖；日志显示逐条处理结果。
6. 打开"丢弃成功回执"开关再同步一次 → 服务器返回 `replay`，无重复事实。
7. 冲突**裁决保持 open** 时用甲再同步一条 → 管理台看到候选数 +1（追加而非覆盖）。
8. 管理台裁决（四种动作均可试），观察统计卡片即时变化、审计流出现完整决定链。
9. 用"管理员补传"通道替设备提交 JSON 批次，验证走同一套幂等与冲突管线。

## 目录结构

```
src/
  shared/          配置与零依赖 HTTP 框架/客户端
  task/            任务服务（设备、任务、归属、领取、审计）
  ingest/          接收入库服务（上传管线、冲突、裁决、统计、审计）
  web/             网关 + 前端静态资源（client/admin）
scripts/           seed.js 虚构种子；dev.js 三进程并行启动
test/e2e.test.js   端到端测试
data/              运行期 SQLite（已 gitignore）
```
